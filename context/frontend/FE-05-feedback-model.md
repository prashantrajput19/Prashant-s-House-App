# FE-05 — `frontend_Feedback_model_should_create_an_instance`

**Status:** Failing · **File:** `angularapp/src/app/models/feedback.model.ts` · **Export:** `Feedback`

## What the test does

```ts
const feedback: Feedback = {
  feedbackId: 1,
  feedbackText: 'Excellent design and architecture!',
  date: '2025-01-22T10:00:00.000Z',
  user: { userId: 123 },
  architect: { architectId: 987 },
  category: 'Service'
};
// feedbackText, date, user, architect, category each toBeDefined()
```

## Why it fails today

`angularapp/src/app/models/` does not exist.

## What to implement

```ts
export interface Feedback {
  feedbackId?: number;
  feedbackText: string;
  date: string;
  user: { userId: number };
  architect?: { architectId: number };
  category: string;
}
```

Matches the SRS p.15 interface exactly — no additions needed, unlike FE-04.

## Files

**Create:** `angularapp/src/app/models/feedback.model.ts`
**Modify:** nothing.

## Gotchas

- `date` is a **`string`** (ISO 8601), not a `Date`. Keep this consistent with the backend
  `Feedback.date` field, which is also a String (see BE-13).
- `user` is required and shaped `{ userId: number }`; `architect` is **optional** — feedback can be
  about the service generally rather than one architect (SRS). The spec supplies both, so either
  works for the test, but follow the SRS.
- Here the inline `{ userId: number }` shape is correct — unlike FE-04, the spec passes exactly one
  key per nested object, so `Partial<User>` is not required (though it would also compile).
- `feedbackId` optional — auto-generated by the backend.

The add-feedback form, category dropdown, the admin feedback table, `FeedbackService` (FE-09),
